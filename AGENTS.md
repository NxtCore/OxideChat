# AGENTS.md

## Performance Guidelines

- Avoid unnecessary `clone()` calls - prefer borrowing with `&T` or `&mut T`
- Use `&str` instead of `String` in function parameters unless ownership is required
- Only clone `Arc<T>` when spawning new tasks - Arc cloning is cheap but still unnecessary if not spawning
- `PgPool` is already Arc-based internally - never clone it, just use `&pool`
- Preallocate `Vec` capacity with `Vec::with_capacity(n)` when size is known
- Use iterator adapters (`.map()`, `.filter()`, etc.) instead of manual loops where possible
- Prefer `&[T]` over `&Vec<T>` in function parameters
- Use `Cow<str>` when you might need to own or borrow strings conditionally
- Avoid `to_string()` and `to_owned()` unless actually transferring ownership
- Use `query_as` or `query_as!` for type-safe database queries
- Batch database operations - avoid N+1 queries by using `ANY($1)` or `IN` clauses
- Use database transactions for multi-step operations that must be atomic
- Return `Result<T, E>` instead of unwrapping - never panic in production code
- Use `async move` blocks only when necessary - prefer borrowing in async functions
- Do not introduce `Mutex` synchronization; use ownership, channels, atomics, or lock-free primitives instead

## Architecture

- `src/main.rs` - Application entry point, sets up Axum server and database pool
- `src/i18n.rs` - Global i18n translation service (singleton pattern); `load_current_user` runs each request in the user's language (`user_preferences.language`, else the installation default), which `translate` and `Language::current()` read, so `/base` returns that language and `default_language`
- `src/jobs.rs` - Background job scheduler using tokio tasks
- `src/types/` - Shared request/response DTOs and domain types
- `src/tests/` - Unit tests organized by module (e.g., `i18n.rs`, `base.rs`)
- `src/types/budgets/` - Budget definitions, assignments (user, team, API key) and spend evaluation
    - `ledger.rs` - `BudgetLedger`: one Tokio actor reserves estimated cost at admission, reconciles once to actual cost, and refunds on drop; web chat and the gateway both reserve through `BudgetLedger::reserve_for_model`, never through their own checks, once per upstream request (web chat reserves again before every tool step, and a refused step saves the answer so far)
    - `repository.rs` - `Budget::evaluate`/`status_for`/`checks` load effective budgets for a `BudgetSubject` (optional user, optional key)
- `src/types/gateway/` - Gateway rate limiting and credentials, re-exported through `crate::types::*`
    - `limiter.rs` - Admission owned by one Tokio actor; bounded admission and unbounded release/reconciliation channels replace shared locking
    - `policy.rs` - Team and key rate rules, validated policies (`GatewayRatePolicy::from_stored`), and `GatewayLimitError`
    - `estimate.rs` - Token estimation for inference requests; non-chat requests (`media_estimate`, `MediaKind`) add `UnitEstimate` units (one request, rerank searches, audio seconds and audio tokens from the upload size, speech characters, images) to the text estimate, and `ModelPricing::estimate_cost` prices only the units the model has a rate for
    - `form.rs` - `GatewayForm` buffers a multipart request so its `model` can be resolved and rewritten, then re-encodes it under the original request's extensions (keeping the route's body limit) for the Omniference skin to parse
    - `body.rs` - Keeps concurrency reservations alive for the lifetime of HTTP response bodies
    - `repository.rs` - Database access for credentials, policies, and model access; `/models` entries carry Omniference's `type` and `capabilities` (`model_type`) and `?type=` keeps one type (unknown types are 400 `invalid_type`); a key belongs to a user and is pinned to one of their teams (no projects), and authentication requires the user to still be a member of that team
    - `keys.rs` / `keys_repository.rs` - API key management DTOs, errors, and SQL (create, update, revoke, rotate, key-scoped limit rules, per-key budget, team picker); audit events are written to `audit_logs` in the same transaction; every operation takes a `KeyActor` (a `&Uuid` converts to a plain user actor): owners manage their own keys, team admins (`team_members.role = 'admin'`) and installation admins manage service-account keys (`gateway_api_keys.user_id IS NULL`, created with `service_account: true`), and team admins may also revoke members' personal keys and list all keys of their teams (`GatewayTeamKeysResponse`)
    - `admin.rs` / `admin_keys.rs` / `admin_teams.rs` / `admin_audit.rs` - Installation-admin gateway controls under `/api/v1/admin/gateway/...` gated by `admin.developer.*` permissions: all-keys listing and inspection, revoke/disable/enable, team rate rules, concurrency cap and `teams.gateway_enabled`, audit trail view and query-able events (expiring keys, budget thresholds); audit rows are written in the same transaction through `write_admin_audit`, and metadata is run through `redact_metadata`; the limiter reads team policy on every authentication so changes apply to the next request
    - `mod.rs` - Shared gateway types and constants
- `src/types/teams/` - Teams and membership; `team_members.role` is `member` or `admin` (`TeamRole`, `Team::is_admin`, `Team::set_member_role`), and replacing members or a user's teams keeps the roles of members who stay
- `src/types/roles/` - Installation roles (`roles`, `role_permissions`) managed under `/api/v1/admin/roles` and `/api/v1/admin/permissions` (`admin.roles.view` / `.edit`, page `/settings/roles`): built-in roles (`roles.is_builtin`: `admin`, `user`) cannot be renamed or deleted but their permissions can change, no update or delete may leave every role without `admin.roles.edit` (`RoleError::LockOut`; writes take a `SHARE ROW EXCLUSIVE` lock on `role_permissions` so two of them cannot race past the check), a `RoleActor` may only grant or remove permissions it holds itself (wildcards count), and every create, update and delete is audited through `AuditLog::write`; each permission constant in `src/types/permissions/mod.rs` needs a row in the `permissions` seed (a test checks it) and translations `roles.permission.<name>`, grouped by `PermissionResponse::group_of` (`roles.group.<group>`)
- `src/types/request_logs/` - `gateway_request_logs` rows: one row per gateway inference request, keyed by the `x-request-id` the client received (`add_request_id` stores a `RequestLogContext` in request extensions); successes come from `OxideCostSink`, rejections and upstream failures from `RequestLog::record_failure`, and a repeated `request_id` merges into one row
    - `finish_reason` and `time_to_first_token_ms` come from Omniference's `CostRecord` (null on failure rows; a merged row keeps non-null values)
    - Streams dropped before their body ends are logged as `interrupted` by `ReservedBody` (via `RequestLogAbort`); `/models` is not an inference request and is deliberately not logged; `internal` covers database and limiter-unavailable failures
- Service-account keys have no user: `GatewayAuthContext.user_id` is `None`, they authenticate while the team exists and has the gateway enabled, their budget subject is `BudgetSubject::service_key` (own key budgets plus the team's pooled budgets only), and `usage_events.user_id` / `gateway_request_logs.user_id` are nullable (`ON DELETE SET NULL`) so usage is attributed through `team_id` and `api_key_id`; pooled team spend counts usage events recorded for that team (gateway requests use the key's team, web chat uses the user's primary team)
- `src/utils/gateway_limits.rs` - HTTP glue only: admission for a route and Omniference-rendered OpenAI limit headers; protocol formatting belongs to Omniference, not the limiter
- `src/routes/` - HTTP route handlers (handlers only, no type definitions)
    - Handlers take `auth: AuthUser` (`src/types/auth_user.rs`, reads the session user from `RequestContext`; missing user is 401), call `auth.require(&state.db, PERMISSION).await?` (a database failure is a 500, never a 403) and return `Result<Response, AppError>`
    - `AppError` (`src/types/error.rs`) renders the standard JSON error and logs 5xx through `tracing`; use `?` on `sqlx::Error`, `ErrorCode` (`Err(ErrorCode::NotFound.into())`, `.ok_or(ErrorCode::NotFound)?`) and the gateway error enums, `AppError::unique_or(e, ErrorCode::AlreadyExists)` for unique violations, `is_unique_violation` instead of matching error text, and `json_ok(body)` for 200 responses; never `eprintln!`
    - `src/routes/admin/mod.rs` and `src/routes/public/mod.rs` each expose a `router()` that `src/routes/mod.rs` merges; `get_current_user` lives in `src/utils/auth.rs`
- `src/routes/gateway/` - OpenAI-compatible gateway handlers (moved from `src/utils/openai_gateway.rs`)
    - `/anthropic/v1/messages` and `/anthropic/v1/models` (`src/routes/public/anthropic.rs`) serve Anthropic clients such as Claude Code (base URL `/anthropic`) through Omniference's `AnthropicMessagesSkin`, admitted like chat (`GatewayRoute::MESSAGES`, `messages_estimate`) with `anthropic-version`/`anthropic-beta` forwarded and a 32 MiB body limit; `gateway::anthropic::anthropic_compat` accepts the key as `x-api-key` and rewrites the gateway's own OpenAI-shaped refusals into Anthropic error bodies; presets are not applied there and not listed
    - Every inference route goes through `admit_inference` (model access, budget reservation, limiter admission, in that order) and `run_skin`, which hands the request with its `oxide_*` metadata to an Omniference skin handler, so `OxideCostSink` records usage and request logs the same way for every route; each route is a `GatewayRoute` (`INFERENCE`, `for_path`) whose `usage_type` becomes `request_type`
    - `media.rs` runs the non-chat routes through Omniference's skins: JSON `/embeddings`, `/rerank`, `/decisions`, `/images/generations` and `/audio/speech` (`run_json`), multipart `/images/edits`, `/audio/transcriptions` and `/audio/translations` (`run_form`, 25 MiB body limit); presets are chat models and resolve only on `/chat/completions` and `/responses` (`GatewayRoute::accepts_presets`); `/systemone` is not exposed because no OxideChat provider kind speaks it
- `src/types/chat/runner/` - Agent loop for web chat (`prepare_turn`, `stream_turn`): history, request building, tool calls
    - `title.rs`: when the admin setting `title_generation` (`{enabled, model_id}`, in `/api/v1/base` and the admin PATCH) is on, a chat without a title gets one after its first reply from one short request to the chosen model (else the chat's model); it is reserved against and billed to the requesting user's budget (`oxide_request_type = title`), stored only if the chat still has no title, and sent as a `title` SSE event after `done`
    - Sampling is merged request > chat (`chats.sampling`, `ChatSampling`, set via `PUT /api/v1/chats/{id}/sampling`) > model config > model; `ChatSampling.custom` becomes Omniference's `extra_body`, which never overrides reserved keys such as `model` or `stream`
    - The tools a turn may call are the request's (or a locked preset's) plus the admin model config's `enabled_tools` (`turn_tool_ids`); `request_settings.enabled_tools` keeps only the turn's own choice
- Files (`files`, `src/types/files.rs`): one table for every file a user stores, with a `kind` (`image`, `document`) and a `source`. Images keep their bytes (`data` or `file_path`) and may have a caption in `text`; documents keep their extracted `text` and `token_count`, and the original only for a PDF chat attachment uploaded while the admin setting `attachments: {native_pdf}` (in `/api/v1/base` and the admin PATCH, off by default) is on (in `data`; otherwise both byte columns stay NULL). New stored files (knowledge uploads in slice 4) go into this table, not a table of their own. Every upload goes through one route, `POST /api/v1/files?filename=…&purpose=image|icon|chat_attachment` with the raw file as body (25 MiB), handled by `FileUpload::store` and answered with `FileResponse` (`StoredFile`: `kind`, `token_count` for documents, `url` for images); `GET /api/v1/files/{id}` serves an image's bytes (`/api/v1/images/{id}` stays as an alias for links stored earlier), and documents have no bytes to serve. `FileStorage::begin_store` opens the transaction a file is inserted in, serialized per user by an advisory lock, and refuses past 60 uploads per user per hour and a file that does not fit the admin storage quota (`storage: {quota_mb}` in `/api/v1/base` and the admin PATCH, unlimited by default, at least 1; kept bytes plus extracted text count, the new file included); documents check the hourly limit once more before extraction (`FileStorage::check_rate`). Refusals are `FileError`, rendered as `ValidationFailed` (limits: `TooManyRequests`) with `details.reason`, translated as `files.error.<reason>`; the frontend uploads with `postFile` and links with `fileUrl` (`frontend/composables/api/files.ts`)
- Chat file attachments (HEN-22 slice 3, `src/types/chat/attachments.rs`, `files` rows with `source = 'chat_attachment'`): an upload with `purpose=chat_attachment` (`ChatAttachment::upload`) picks the kind from the extension (`DocumentKind::detect`: text and code, HTML, PDF; a PDF must start with `%PDF-`), stores the extracted text with a token estimate for the uploader. HTML and PDF are parsed in a child process (`src/utils/extract.rs`: this binary with the `extract` subcommand, checked in `main` before the Tokio runtime starts, at most 4 at once, no environment, 30 s, 1 GiB address space on Linux, 8 MiB of text at most; PDF pages are marked `<!-- page N -->`, NUL characters are dropped, and a file with only whitespace, such as a scanned PDF, is refused as `empty`), which slice 4 reuses for knowledge uploads. `attachment_cleanup_job` deletes, every hour, attachments of deleted users and those older than a day that no message refers to
    - A user message carries `{type: 'file', attachment_id, filename}` parts; the history (`get_omni_messages`) loads the user's attachments in one query and puts each file's text into the message as data (`ChatAttachment::prompt_text`), no vectors; while `attachments.native_pdf` is on and the model's input modalities (the admin model config's, else Omniference's; vision follows the same list) include `File`, a kept original PDF is sent instead as Omniference's `ContentPart::File` with a base64 data URL (`ChatAttachment::originals`, `file_part`), and budget estimates still count its extracted text. `prompt_bytes` refuses attachments the user does not own (`attachment_not_found`) and, for a turn with attachments, a prompt above the model's context window (`context_too_large`, about four bytes per token); `Message::active_prompt_bytes` counts attached text, so budgets include it. Attaching needs no knowledge setup; the composer has its own button (`composer-attach-file`), shows the files as chips (`attached-file`) and the message shows them as `message-attachment`
- `src/types/tools/` - One file per entity (`tool.rs`, `tool_function.rs`, `tool_execution.rs`, `wasm_blob.rs`, `mcp_server.rs`); `McpScope` (`mcp_scope.rs`) separates admin-wide and per-user MCP servers; MCP servers connect over Streamable HTTP only, and server-side `stdio` servers are refused on create and on connect until they can run in a sandbox
    - Tool requests leave the server through `src/utils/tools/`: the HTTP executor percent-encodes `{{input.x}}` values in the URL and refuses a result that leaves the configured origin or path depth, a function's absolute `entrypoint` must share the tool URL's origin (`http::function_url`), response bodies are read through `outbound::read_limited` (4 MiB for HTTP and MCP tools), and request errors are formatted with `without_url()` so a URL with a secret never reaches the chat
    - A tool that sends paid requests of its own reserves through `ToolContext.budget_ledger` like the image tool does (`imagegen::reserve_budget`, estimate from `image_tool_estimate`) and puts the reservation ID into the request metadata
- Provider-reported cost: `providers.reported_cost` (`ProviderReportedCost`: unit `usd`, `currency` or `credits`, optional `source` path or `header:<name>`) becomes Omniference's `ProviderEndpoint.reported_cost` in `ai::build_engine`, which emits the cost in USD; currencies use `exchange_rates`, refreshed from the ECB by `exchange_rate_job`, and a currency without a rate falls back to token pricing
- Model prices (`ModelPricing`, `src/types/models/repository.rs`): the catalog price Omniference knows for the model's provider (models.dev plus catalog overrides, through `ai::catalog()`), with an optional manual override from `model_pricing_overrides` on top; endpoint rows in `gateway_model_provider_options` are display only. Manual prices are pushed into the engine's catalog keyed by provider name and model ID (`ai::build_engine` loads them all, `ModelPricing::push_to_engine` after every change), so Omniference prices every request itself and `OxideCostSink` stores its cost as is; `ModelPricing` estimates and fallback costs also go through Omniference's `compute_cost` at the current time, so context tiers and time windows apply to budget reservations
    - Prices are `PriceSheet`s (`src/types/models/pricing.rs`): base rates, context `tiers`, `service_tiers` (`flex`, `priority`, ...) and time `windows` (days, `HH:MM` start and end, timezone); token rates are USD per million tokens, the unit rates `per_audio_second`, `per_character`, `per_request` and `per_search` USD per unit and count as charging for budgets; resolved by Omniference as base → context tier → service tier → window. An override is partial: every rate or list it leaves unset (missing or `null`) comes from the catalog, and an empty list replaces the catalog's with none. The merged price is pushed to the engine, so it is recomputed on every save and engine rebuild, not when Omniference refreshes models.dev
    - Overrides are saved through `ModelPricing::save_override` / `store_override` (validated by `PriceSheet::validate`, audited as `model_pricing_updated` / `_deleted`); refusals are `PriceSheetError`, rendered as `ValidationFailed` with `details.reason`, which the frontend translates as `pricing.error.<reason>`
    - The response carries `override_pricing` plus `catalog` and `effective` as `PricedSheet`s (`price` and its `PriceSummary`: input/output ranges and the special rates); the admin editor is `SettingsModelsPricingEditor`, prices and special rates are shown with `formatRange` and `PricingSpecialRates` (`frontend/utils/pricing.ts`), and the Developer models list returns the same summary as `price`
- `src/types/provider_routing/` - Upstream provider routing for provider kinds that route on to upstream providers (`ProviderKind::UPSTREAM_ROUTING`, `routes_upstream()`: `OPENROUTER` and `CORTECS`). The installation (`provider_routing: {selector_enabled, allowed_providers}` in `/api/v1/base` and the admin PATCH) and each team (`teams.provider_selector_enabled`, `teams.allowed_upstream_providers`) set whether users get the chat provider selector and which upstream providers requests may reach; `EffectiveProviderRouting::combine` intersects the allowlists and lets a team's "off" win. `ProviderRoutingMiddleware`, registered on the engine in `ai::build_engine`, restricts every request's `ChatRequestIR::provider_routing` to that allowlist (gateway: the key's team; web chat and titles: all of the user's teams) and refuses others with a 403
    - Allowlists are kept per routing provider kind (`ProviderAllowlists`, `{OPENROUTER: [...]}`; a kind without an entry is unrestricted; installation in `app_config.allowed_upstream_providers`, teams in the JSONB `teams.allowed_upstream_providers`); an allowed slug also allows its variants (`deepinfra` allows `deepinfra/fp8`)
    - `sources/`: each kind's `sync` function (dispatched by `sources::sync`) fetches its upstream providers (OpenRouter: `/v1/providers`; Cortecs, which has no provider list or names: the union of `providers` from `/v1/models?extended=true`, slug as name). `POST /api/v1/admin/upstream-providers/sync` and, in a background task, every model sync of a routing provider store the result in `upstream_gateways` / `upstream_providers`; `GET /api/v1/admin/upstream-providers` lists it, falling back to the endpoint options for kinds never synced. Restrictions the routing provider itself puts on our key (OpenRouter guardrail policies) are not read
    - To add a routing provider (e.g. Vercel): add its kind to `UPSTREAM_ROUTING`, map `ProviderRouting` in its Omniference adapter or vendor dialect, and add a `sync` function in `sources/` called from `sources::sync`
    - Cortecs (`CortecsDialect` in Omniference, Responses adapter): `only` becomes `allowed_providers`, `order` becomes `allowed_providers` with `provider_order: "custom"`, and Cortecs never falls back beyond that list, so web chat's "prefer" puts the model's other stored providers the user may use after the picked one (`picked_provider`); "lock" stays `only: [slug]`. Its catalog and every model's provider options come from one `/v1/models?extended=true` call in the model sync (`sync_cortecs_catalog`, `source_gateway = 'cortecs'`, `cortecs_options`, written in one transaction by `GatewayCatalogModel::replace_gateway_provider_options`); the provider-options refresh re-runs that sync. Cortecs reports EUR per 1M tokens (converted to USD with `exchange_rates`, left empty without a rate), latency in seconds (stored as ms) and uptime as a fraction (stored as percent); `ttft` and `cache_hit_rate` stay in `raw`. The admin Catalog tab stays OpenRouter-only
- Provider kinds without their own Omniference adapter pass `ProviderKind::catalog_slug()` as `catalog_provider_slug`, the vendor slug Omniference uses for models.dev prices and its vendor profile (`catalog/providers/<slug>.toml`); every `ProviderConfig` OxideChat builds must set it (`profile` and `resolved_profile` stay `None`: registration resolves the profile). `MISTRAL` uses the OpenAI-compatible Chat adapter (`/v1/chat/completions`), where Omniference's `MistralDialect` applies; `CORTECS` uses the OpenAI Responses adapter (`/v1/responses`)
- `src/types/rag/` - Knowledge (RAG, HEN-22, built as stacked PRs; slices 1, 2a, 2b, 2c and 2d so far): `rag_config` (single row: reranker model and `top_n`, default connection) and `rag_connections` (where vectors live), managed under `/api/v1/admin/rag` (`admin.rag.view` / `.edit`, page `/settings/tools/knowledge`, a sub page of Tools; `/settings/knowledge-setup` redirects there); knowledge is on while the Knowledge Search builtin tool row is enabled (`RagConfig::enabled`, `Tool::builtin_enabled`), there is no separate switch, and `/api/v1/base` returns that as `rag: {enabled}`
    - A connection has a `kind` (`pgvector`, `qdrant`) and a `mode` (`managed`: `OxideChat` writes, pgvector only; `read_only`: another pipeline fills it), both fixed at create. Its URL never holds a password, and a pgvector URL takes no query parameter but `sslmode` and no percent-encoded host (sqlx would read host, port, socket and key files from them past the host checks): the Postgres password or Qdrant API key is the encrypted `secret`, a new host needs it again (`RagConnection::redirects_secret`), and Qdrant keys go over https only. A managed pgvector connection without URL is the main database; `RAG_PGVECTOR_URL` replaces the address and password of the default managed connection
    - A managed connection's embedding model is checked with one test embedding billed to the saving admin (`probe_embedding`, `oxide_request_type = rag_setup`), which stores `vector_size`; a new model or size bumps `index_generation`. Reranker and embedding models are checked with `gateway::model_type`, and the admin model list takes `?type=embedding|reranking` for the pickers
    - `VectorStore` (`store.rs`) opens a connection for `health` (pgvector 0.8+ or the Qdrant version), `list_collections`, `describe` (vectors with size and distance, payload field paths, three sample records without vectors and with strings cut by `shorten`) and `search` (nearest records as payload and score, inside the view's fixed filter); addresses follow the outbound rules (`private_hosts_allowed`), read-only Postgres sessions set `default_transaction_read_only`, external pgvector pools are reused per address, secret and mode (`PG_POOLS`, an `ArcSwap` map; the host check still runs on every connect and idle connections close after a minute), and failures are `StoreError` codes (`rag.store_error.<code>`), never the server's own text. Validation failures are `RagError`, rendered as `ValidationFailed` with `details.reason` (`rag.error.<reason>`)
    - pgvector tables are resolved with `to_regclass` and their columns read from `pg_attribute`; identifiers go into SQL only through `quote_ident` after that lookup, filter values only as parameters (`view::pg_filter`, which refuses unknown columns), and search sets `hnsw.iterative_scan = relaxed_order` in its transaction (pgvector below 0.8 answers `extension_too_old`). Qdrant runs over REST (`/collections/{name}`, `/points/scroll`, `/points/query`) with the view's filter as `must` conditions (`view::qdrant_filter`)
    - Knowledge bases (slice 2a, `knowledge_bases.rs`, `knowledge_bases` / `knowledge_base_shares`): a view (`ExternalView`: connection, collection, optional `vector_name`, `distance`, the `embedding` model that built the collection, `fields: {text, title?, url?, section?}` as dotted payload paths, fixed `filter` of field = value conditions; pgvector compares them as JSON (`pg_filter`), so a dotted path reaches into a JSON column and `5` matches `5.0`) onto a read-only connection's collection, under `/api/v1/knowledge-bases` (page `/settings/knowledge`). Only knowledge admins (`admin.rag.edit`) create, delete, change the source and share; `check_view` checks the collection, the vector and one test embedding whose size must match (`collection_dimensions_mismatch`). A new knowledge base is shared with nobody; sharing goes through `…/assignments` with everyone, teams, roles and users, each as `viewer` or `editor` (editors change name and description; everyone is viewer only), and, while the view has no per-record access, the frontend asks for a confirmation before a share with everyone, a team or a role because source access rights are not checked. `admin.rag.view` (and `admin.rag.edit`, which includes seeing what it edits) sees every knowledge base with its source; other users see only those shared with them and never the connection or view. `POST …/{id}/search` is the test search, for bases shared with the user or by `admin.rag.edit` (`KnowledgeActor::can_search`; `admin.rag.view` alone is not enough): one query embedding billed to the user as `rag_query`, hits mapped through `ExternalView::hit` (only `http(s)` links; Qdrant Euclid and Manhattan distances are negated so higher is closer). A connection cannot be deleted while knowledge bases use it (`connection_in_use`)
    - Knowledge tool (slice 2b, `retrieval.rs`): knowledge bases are attached to chats (`chat_knowledge_bases`, replaced by `StreamRequest.knowledge_base_ids`, returned as `ChatWithMessagesResponse.knowledge_base_ids`) and presets (`preset_knowledge_bases`, `SavePresetRequest.knowledge_base_ids`; only bases the saving user may search are added, ones already attached stay). `prepare_single` keeps the attached bases the user may search right now (`turn_knowledge_bases`: none while the Knowledge Search tool is off) and offers `knowledge_search` (`add_knowledge_tool`: `query`, optional `knowledge_base` name from an enum, replacing the stored spec or a user tool of the same name, which the agent also never runs while the tool is offered) only when some remain, the model does not list capabilities without `TOOLS` (a model with none, such as a self-hosted one, still gets it) and the Knowledge builtin tool is among the turn's tools (`offer_knowledge`, `Tool::enabled_builtin_among`: an enabled system tool row with `builtin_id = knowledge` named `knowledge_search`, created from its template in `useBuiltinToolTemplates` on Settings → Tools, whose row links to the knowledge setup at `/settings/tools/knowledge` and is never run through `get_builtin_executor`); like other tools it comes from the request, a preset or the admin model config, and attaching a base in the composer or the preset editor selects it; arena turns never get it. The agent runs the tool itself (`run_knowledge_tool`, never through `get_builtin_executor`; `resolve_tools` skips the row, so neither its spec nor its system prompt reaches a turn that does not offer the tool): it checks the bases again, narrows them by the model's argument, embeds the query once per distinct embedding model, searches every base in parallel (one whose store is unreachable or whose embedding model fails is listed under `unavailable`; a used-up budget fails the tool), merges with RRF (identical text once), keeps at most 3 excerpts per document and 20 candidates, reranks them with the configured reranker down to its `top_n` (else keeps 8; a failed rerank keeps the merged order) and numbers the sources `[n]` up to 16,000 characters with each excerpt cut to 4,000, wrapped with a note that they are data, not instructions. Query embedding and rerank reserve budget as `rag_query`. `KnowledgeBaseResponse.usable` marks bases shared with the viewer; the composer lists those in `ChatSettingsMenu` (`useKnowledgeStore`, `composer-knowledge-<name>`, chip `knowledge`), the preset editor in its Knowledge tab (`SettingsPresetsKnowledgeTab`), and `ToolExecutionDisplay` shows a `knowledge_search` result as source chips. The e2e stand-in calls `knowledge_search` once when it is offered and answers from the first source

## Code Organization

### Types Module (`src/types/`)

- All request/response structs live in `src/types/`, not in route files
- Organized by domain: `i18n.rs`, `base.rs`, etc.
- `src/types/mod.rs` re-exports all types for easy importing: `use crate::types::*;`
- Each file uses section comments for clarity:
    - Request Types (structs with `Deserialize`)
    - Response Types (structs with `Serialize`)
    - Internal Types (DB row structs, helper functions)
- Group related fields of a request or response into a nested object instead of prefixing flat field names: `instance: {name, icon_id}`, not `instance_name` and `instance_icon_id`; requests use the same shape as the response they update

### Tests Module (`src/tests/`)

- Unit tests live in `src/tests/`, not inline in route files
- One test file per module: `i18n.rs`, `base.rs`
- Use `#[cfg(test)]` wrapper for all test code
- Group related tests in submodules: `mod types { ... }`
- Import types via `crate::types::*`

### Route Files (`src/routes/`)

- Contain only handler functions, no struct definitions
- Import types from `crate::types::{...}`
- Keep handlers thin: validate → delegate → respond
- ABSOLUTLY NO direct database access in route files, all database access is handled via the data/types model

### Data Model Pattern

* **Structure:** Locate domain models and their `impl` blocks in `src/types/` (e.g., `user.rs`).
* **Logic:** Use associated functions (`::`) for queries/constructors and instance methods (`.`) for operations on specific records.
* **State:** Pass `&PgPool` explicitly as a parameter; never rely on global database state.
* **Mapping:** Implement `to_response` methods within the model to handle DTO transformations.
* **Encapsulation:** Keep all SQL logic and business rules for a type within its dedicated file.

## Code Quality

- Clippy lints are enforced: `correctness` and `suspicious` are denied, `perf` and `style` are warnings
- Cognitive complexity threshold: 15
- Max function arguments: 5 (use structs for more)
- Max function lines: 100
- Document public APIs with `///` doc comments
- Include `# Errors` and `# Panics` sections in documentation where applicable
- Use `#[must_use]` for functions whose return value should not be ignored
- Prefer explicit types over `_` in public APIs
- Use `thiserror` or similar for custom error types
- Do not use static strings, use the i18n system instead

## Testing

- Use `#[sqlx::test]` for database tests - provides isolated test database
- Use `#[tokio::test]` for async tests
- Tests live in `src/tests/` with one file per module
- Group related tests in submodules: `mod types { }`, `mod handlers { }`

## Important Notes

- Always use parameterized queries (`$1`, `$2`) to prevent SQL injection
- Never use `unwrap()` or `expect()` in production code paths
- Job scheduler runs indefinitely - ensure jobs handle errors gracefully
- Database URL must be set in `.env` file as `DATABASE_URL`
- Migrations run automatically on startup
- Keep the code as simple as possible so beginners can also understand it
- Do not add comments to the code itself
- When writing axum routes, please use the response "module" to create responses
- NO SQL statements in route handlers, please add a function to the specific type's module for database operations (check if a smilar function already exists)

## Local Development

- Until the first release, schema changes, translations and data fixes are folded into `migrations/20251226000000_initial_schema.sql` and development databases are recreated; after it they go into a new file under `migrations/`
- The Docker image trusts `X-Forwarded-For` only from the ranges in `TRUSTED_PROXIES` (the start script writes them as `set_real_ip_from` lines that `nginx.conf` includes); it is empty by default
- Omniference is a major part of the application; developers may point Cargo at a local checkout with a patch override in `.cargo/config.toml`
- A local reverse proxy must forward `/api`, `/openai` and `/anthropic` to the backend, as `nginx.conf` does; otherwise the Playground gets a 404 from Nuxt
